# 7. FILE-BY-FILE BREAKDOWN

## src/services/mlRecommend.ts — Core ML Recommendation Engine

**Purpose:** An in-browser machine learning recommendation system that finds clothing items matching a user's natural language query using TF-IDF, Latent Semantic Analysis (SVD), and KMeans clustering.

**Why In-Browser?** The product catalog is only 30 items. Running the entire ML pipeline in JavaScript on the user's device takes < 10 milliseconds. No server round-trip, no latency, no cost.

**Input:**
```typescript
function mlRecommend(
  query: string,           // e.g., "casual blue winter shirt"
  products: Product[],     // 30-shirt catalog
  topK: number = 5,        // number of results to return
  modelParams: ModelParams  // pre-computed ML matrices from modelParams.json
): ScoredProduct[]
```

**Output:**
```typescript
interface ScoredProduct {
  product: Product;       // full product object
  score: number;          // 0.0-1.0 relevance score
  attributeScore: number; // keyword match score
  lsaScore: number;       // semantic similarity score
  rank: number;           // 1-indexed rank
}
```

### Step-by-Step Pipeline

#### Step 1: Query Tokenization
```typescript
function tokenize(query: string): string[] {
  const normalized = query.toLowerCase().trim();
  const words = normalized.split(/\s+/).filter(w => w.length >= 2);
  const bigrams = [];
  for (let i = 0; i < words.length - 1; i++) {
    bigrams.push(`${words[i]} ${words[i+1]}`);
  }
  return [...words, ...bigrams];
}
```
- Input: "casual blue winter shirt"
- Output: ["casual", "blue", "winter", "shirt", "casual blue", "blue winter", "winter shirt"]
- Bigrams (two-word pairs) capture phrases like "winter shirt" which has different meaning than just "winter" + "shirt"

#### Step 2: TF-IDF Vectorization
```typescript
function tfidfVectorize(tokens: string[], modelParams: ModelParams): number[] {
  const vocab = modelParams.vocabulary;       // term → index mapping
  const idf = modelParams.idfVector;          // precomputed IDF weights
  
  // Count term frequencies
  const tf: Record<number, number> = {};
  tokens.forEach(token => {
    const idx = vocab[token];
    if (idx !== undefined) tf[idx] = (tf[idx] || 0) + 1;
  });
  
  // Sublinear TF: 1 + log(count) instead of raw count
  // This prevents "shirt shirt shirt" from dominating
  const vector = new Array(idf.length).fill(0);
  Object.entries(tf).forEach(([idx, count]) => {
    vector[Number(idx)] = (1 + Math.log(count)) * idf[Number(idx)];
  });
  
  // L2 normalize
  return l2Normalize(vector);
}
```

**What is TF-IDF?**
- **TF (Term Frequency):** How often a word appears in the query
- **IDF (Inverse Document Frequency):** How rare the word is across all shirts (log(N/df))
  - "shirt" appears in all 30 shirts → low IDF (common word, not informative)
  - "flannel" appears in 3 shirts → high IDF (rare word, very informative)
- **TF-IDF Score = TF × IDF** — Words that are frequent in the query AND rare in the catalog score highest

#### Step 3: SVD Transform (Latent Semantic Analysis)
```typescript
function svdTransform(tfidfVector: number[], svdComponents: number[][]): number[] {
  // Matrix multiply: query_tfidf (1×V) × svdComponents^T (V×K) = query_lsa (1×K)
  return svdComponents.map(component =>
    tfidfVector.reduce((sum, val, i) => sum + val * component[i], 0)
  );
}
```

**What is SVD/LSA?**
- SVD (Singular Value Decomposition) is a mathematical technique that reduces a high-dimensional space to a lower-dimensional "latent" space
- In text, it groups synonyms and related concepts:
  - "shirt" and "blouse" map to similar latent directions
  - "casual" and "relaxed" map to similar latent directions
- This means a query "relaxed fit top" can still match "casual loose shirt" even without exact word overlap
- This is called **Latent Semantic Analysis (LSA)**

**Practical Effect:** Semantic search — understanding meaning, not just word matching.

#### Step 4: Attribute Keyword Scoring
```typescript
function scoreByAttributes(query: string, product: Product): number {
  const q = query.toLowerCase();
  let matches = 0;
  let total = 0;
  
  const attributes = [
    { field: product.color, weight: 2 },
    { field: product.name, weight: 1 },
    { field: product.style, weight: 2 },
    { field: product.pattern, weight: 1.5 },
    { field: product.fabric, weight: 1.5 },
    { field: product.occasion, weight: 2 },
    { field: product.description, weight: 0.5 }
  ];
  
  attributes.forEach(({ field, weight }) => {
    total += weight;
    if (field && q.includes(field.toLowerCase())) {
      matches += weight;
    }
  });
  
  return matches / total;
}
```

- Higher weights on color, style, and occasion because users explicitly mention these
- Lower weight on description because it's verbose and less precise
- Returns 0.0-1.0 normalized score

#### Step 5: Cold Fabric Detection
```typescript
const COLD_FABRICS = ['flannel', 'wool', 'velvet', 'fleece', 'corduroy'];

function isColdFabric(fabric: string): boolean {
  return COLD_FABRICS.some(f => fabric.toLowerCase().includes(f));
}
```

Used for weather-based filtering. When `weather.temperature < 15°C` or `quizDetails.season === 'Winter'`, cold fabric shirts get a scoring bonus.

#### Step 6: Hybrid Scoring
```typescript
function hybridScore(attributeScore: number, lsaScore: number, hasAttributeMatch: boolean): number {
  if (hasAttributeMatch) {
    // Attribute match found: 70% keyword + 30% semantic
    return 0.7 * attributeScore + 0.3 * lsaScore;
  } else {
    // No keyword match: fall back to pure semantic
    return lsaScore;
  }
}
```

**Why 70/30 Split?**
- Explicit keyword matches (color name, occasion) are highly reliable signals
- LSA semantics are valuable for finding related items the user didn't explicitly name
- When both signals exist, attribute matching dominates (more precise)
- When no keywords match, semantic search provides a meaningful ranking

#### Step 7: KMeans Cluster Bonus
```typescript
function findNearestCluster(lsaVector: number[], kmeansCenters: number[][]): number {
  let minDist = Infinity;
  let nearestCluster = 0;
  kmeansCenters.forEach((center, i) => {
    const dist = euclideanDistance(lsaVector, center);
    if (dist < minDist) { minDist = dist; nearestCluster = i; }
  });
  return nearestCluster;
}

// Apply bonus
if (product.cluster === predictedCluster) {
  score += CLUSTER_BONUS; // typically 0.1-0.2
}
```

KMeans clustering groups shirts into style clusters (e.g., "casual cluster", "formal cluster"). If the query's LSA vector falls near the same cluster as a shirt, that shirt gets a small bonus — a tiebreaker for similar scores.

3. All matrices serialized to JSON
4. Frontend imports and uses directly

### Section 2: Feature Engineering
```python
from sklearn.feature_extraction.text import TfidfVectorizer

# Combine all text features into one string per shirt
def shirt_to_text(shirt):
    return f"{shirt['name']} {shirt['color']} {shirt['style']} {shirt['fabric']} {shirt['occasion']} {shirt['description']}"

texts = [shirt_to_text(s) for s in shirts]

# Fit TF-IDF
vectorizer = TfidfVectorizer(
    ngram_range=(1, 2),    # unigrams + bigrams
    sublinear_tf=True,      # 1 + log(tf)
    min_df=1,
    max_features=2000
)
tfidf_matrix = vectorizer.fit_transform(texts)
```

### Section 3: Dimensionality Reduction (LSA)
```python
from sklearn.decomposition import TruncatedSVD
from sklearn.preprocessing import normalize

svd = TruncatedSVD(n_components=50)   # Reduce to 50 latent dimensions
lsa_matrix = svd.fit_transform(tfidf_matrix)

```

### Person Parsing Cache (LRU)

```python
from functools import lru_cache

@lru_cache(maxsize=8)
def parse_person_cached(image_hash: str, image_bytes: bytes) -> np.ndarray:
    """Cache person parsing results for 8 most recent persons.
    
    Person parsing is expensive (~5 seconds). If the user uploads the same
    photo multiple times (e.g., trying different garments), we skip recomputation.
    """
    return parse_person_with_onnx(image_bytes)
```

**Why Useful:** A user might try on 3-4 different shirts in one session using the same photo. Without caching, each try-on would re-run the 5-second person parsing step. With LRU cache of size 8, the same person image is parsed only once per session.

### Try-On Endpoint

```python
@app.function(...)
@modal.web_endpoint(method="POST")
def tryon_endpoint(request: TryOnRequest) -> TryOnResponse:
    """
    POST /tryon
    
    Input:
    {
        "person_image": "base64_encoded_png",
        "garment_image": "base64_encoded_png",
        "category": "upper_body" | "lower_body" | "dresses",
        "num_steps": 20,
        "guidance_scale": 2.0,
        "seed": 42
    }
    
    Output:
    {
        "result_image": "base64_encoded_png",
        "generation_time": 45.2,
        "steps_completed": 20
    }
    """
    
    # 1. Parse base64 images → PIL Images
    person_img = decode_base64_image(request.person_image)
    garment_img = decode_base64_image(request.garment_image)
    
    # 2. Parse person (or use LRU cache)
    person_hash = hash(request.person_image)
    person_parse = parse_person_cached(person_hash, request.person_image)
    
    # 3. Clean garment image (remove non-garment pixels)
    cleaned_garment = clean_garment_with_onnx(garment_img)
    
    # 4. Run OOTDiffusion
    result = ootd_pipe(
        image=person_img,
        cloth=cleaned_garment,
        category=request.category,
        num_inference_steps=request.num_steps,
        guidance_scale=request.guidance_scale,
        generator=torch.Generator("cuda").manual_seed(request.seed)
    )
    
    # 5. Optional: Stable Diffusion + ControlNet refinement
    if request.apply_refinement:
        result = refine_with_sd(result, garment_img)
    
    # 6. Encode and return
    return TryOnResponse(result_image=encode_base64_image(result))
```

### Garment Cleaning Pipeline

```python
def clean_garment_with_onnx(garment_img: PIL.Image) -> PIL.Image:
    """Remove human body pixels from garment-on-model images.
    
    Input: Garment photo (may show a model wearing it)
    Output: Garment image with non-garment areas made transparent
    """
    
    # 1. Resize to model input size (512×512)
    img_array = preprocess_image(garment_img)
    
    # 2. Run ONNX ATR human parser
    ort_inputs = {'input': img_array}
    parse_result = ort_session.run(None, ort_inputs)[0]
    
    # 3. Create binary mask (garment pixels = 1, non-garment = 0)
    garment_mask = (parse_result == GARMENT_LABEL).astype(np.uint8)
    
    # 4. Apply mask → transparent background
    garment_clean = apply_mask_to_image(garment_img, garment_mask)
    
    return garment_clean
```

**Why Garment Cleaning Matters:** Stock photos of clothes often show them on a model. If we feed this directly to OOTDiffusion, the model body from the stock photo might bleed through onto our user's photo. Cleaning removes the model and extracts just the garment shape.

### SD + ControlNet Refinement Pass

```python
def refine_with_sd(tryon_result: PIL.Image, garment_img: PIL.Image) -> PIL.Image:
    """Post-process try-on with Stable Diffusion + ControlNet-Canny.
    
    The base OOTDiffusion result can sometimes have soft garment edges.
    This pass sharpens the garment texture using edge-guided generation.
    """
    
    # 1. Extract edges from garment (Canny edge detection)
    garment_edges = cv2.Canny(np.array(garment_img), 100, 200)
    canny_image = PIL.Image.fromarray(garment_edges)
    
    # 2. Run ControlNet + SD for texture refinement
    refined = sd_pipe(
        prompt="A person wearing a high-quality garment, photorealistic, detailed fabric texture",
        image=tryon_result,           # Starting from OOTDiffusion result
        control_image=canny_image,    # Guide with garment edges
        controlnet_conditioning_scale=0.8,
        num_inference_steps=15,       # Fewer steps (refinement, not full generation)
        strength=0.3,                 # Low strength (mostly preserve OOTDiffusion result)
    ).images[0]
    
    return refined
```

### Garment Category Detection Endpoint

```python
@app.function(...)
@modal.web_endpoint(method="POST")
def detect_category_endpoint(request: CategoryRequest) -> CategoryResponse:
    """
    POST /detect-category
    
    Uses the ONNX ATR parser to classify what type of garment is shown.
    
    Returns: "upper_body" | "lower_body" | "dresses"
    """
    img = decode_base64_image(request.garment_image)
    parse_result = ort_session.run(None, {'input': preprocess_image(img)})[0]
    
    # Count pixels of each category in parse result
    upper_pixels = np.sum(parse_result == UPPER_BODY_LABELS)
    lower_pixels = np.sum(parse_result == LOWER_BODY_LABELS)
    dress_pixels = np.sum(parse_result == DRESS_LABELS)
    
    dominant = max(upper_pixels, lower_pixels, dress_pixels)
    if dominant == upper_pixels: return CategoryResponse(category="upper_body")
    if dominant == lower_pixels: return CategoryResponse(category="lower_body")
    return CategoryResponse(category="dresses")
```

## src/hooks/useWeather.ts — Weather Integration

**Purpose:** Custom React hook providing current weather data for the user's location. Powers weather-aware outfit recommendations.

**Full Implementation Flow:**

```typescript
function useWeather(): WeatherData {
  const [weather, setWeather] = useState<WeatherData | null>(null);
  
  useEffect(() => {
    // LEVEL 1: Instant IP-based weather (no permission needed)
    fetch(`https://api.weatherapi.com/v1/current.json?key=${WEATHER_API_KEY}&q=auto:ip`)
      .then(r => r.json())
      .then(data => {
        setWeather({
          temperature: data.current.temp_c,
          description: data.current.condition.text,
          iconUrl: `https:${data.current.condition.icon}`,
          location: data.location.name,
          country: data.location.country
        });
      });
    
    // LEVEL 2: Precise GPS weather (requires browser permission)
    navigator.geolocation.getCurrentPosition(
      (position) => {
        const { latitude, longitude } = position.coords;
        fetch(`https://api.weatherapi.com/v1/current.json?key=${KEY}&q=${latitude},${longitude}`)
          .then(r => r.json())
          .then(data => setWeather(/* precise weather */));
      },
      (error) => {
        // Level 1 fallback remains active
        console.log('Geolocation denied, using IP weather');
      }
    );
  }, []);
  
  return weather;
}
```

**Why Two Levels?** 
- IP geolocation is fast (instant result) but less accurate (may be off by 50-100km)

# 8. AI/ML SYSTEM DEEP DIVE

## Understanding TF-IDF

**Definition:** Term Frequency-Inverse Document Frequency. A numerical statistic that reflects how important a word is to a document in a collection.

**Intuition Example:**
- Corpus: 30 shirt descriptions
- Query: "casual blue winter shirt"

| Term | TF in Query | DF in Corpus | IDF | TF-IDF |
|---|---|---|---|---|
| "shirt" | 1 | 30/30 | log(1) = 0 | 0 |
| "casual" | 1 | 25/30 | log(30/25) = 0.18 | 0.18 |
| "blue" | 1 | 12/30 | log(30/12) = 0.40 | 0.40 |
| "winter" | 1 | 8/30 | log(30/8) = 0.57 | 0.57 |

"winter" has the highest TF-IDF because it's the most specific/rare term. The query vector emphasizes winter heavily, so winter shirts rank highest.

## Understanding SVD/LSA

**The Vocabulary Size Problem:** After TF-IDF, the query is a vector of size ~2000 (one dimension per vocabulary term). Computing similarities in 2000 dimensions is computationally expensive and suffers from the "curse of dimensionality."

**SVD Solution:** Find the most important 50 dimensions (latent topics) that explain most of the variance in the text.

**Semantic Effect:**
```
Before SVD:
  "casual" → dimension 47
  "relaxed" → dimension 891
  These have zero overlap! Similarity = 0

After SVD:
  "casual" → [0.3, -0.1, 0.5, ...]  (50-dim vector)
  "relaxed" → [0.28, -0.09, 0.47, ...]  (similar pattern)
  Cosine similarity = high!
```

SVD captures that "casual" and "relaxed" appear in similar contexts across the corpus, so they map to similar latent dimensions. This enables semantic matching.

## Understanding KMeans

**What It Does:** Groups the 30 shirts into K clusters (K=5 in this project) based on their LSA vectors. Shirts with similar style profiles end up in the same cluster.

**Example Clusters:**
- Cluster 0: Casual cotton shirts (blue, gray, navy)
- Cluster 1: Smart casual / business casual
- Cluster 2: Formal shirts (white, light blue)
- Cluster 3: Sporty / active wear shirts
- Cluster 4: Winter / warm fabric shirts

**Usage in Recommendation:** When a query's LSA vector maps to Cluster 0 (casual), shirts in Cluster 0 get a +0.15 bonus. This is a soft constraint — other clusters can still appear if their scores are high enough.

## Cosine Similarity

**Definition:** Measures the angle between two vectors. Value between -1 and 1. In NLP, 1 = identical meaning, 0 = completely unrelated, -1 = opposite.

**Formula:**
```
cosine(A, B) = (A · B) / (|A| × |B|)
```

**In Practice:** We pre-compute and L2-normalize all shirt LSA vectors (stored in `lsaMatrixNorm`). For a new query, we:
1. Project query through SVD → query LSA vector
2. L2-normalize query LSA vector
3. Dot product with each shirt's normalized LSA vector
4. Result = cosine similarity (since both are normalized, |A| × |B| = 1)

L2-normalization converts the dot product to cosine similarity without division at query time.

## OOTDiffusion — The Core Try-On Model

**Full Name:** Open Outfit Try-On Diffusion

**Architecture:** Based on Stable Diffusion with custom conditioning for garment fitting. Uses two key innovations:
1. **Outfitting Fusion:** Cross-attention between the person's body features and the garment features
2. **Outfitting UNet:** Modified UNet that conditions generation on both body pose and garment appearance

**Training Data:** VITON-HD dataset — 13,000 high-resolution image pairs (person + garment + try-on result)

**Input Requirements:**
- Person image: 768×1024 pixels, person centered, clear upper body

- `num_inference_steps` (default: 20) — More steps = better quality but slower
- `guidance_scale` (default: 2.0) — How closely to follow the garment's appearance

# 16. COMMON ERRORS & DEBUGGING GUIDE

## ML Recommendation Issues

### No recommendations returned
**Cause:** Query terms not in vocabulary (e.g., very unusual words)
**Fix:** Check `modelParams.vocabulary` for the query terms. If missing, expand the product catalog and re-run the notebook to regenerate `modelParams.json`.

### All recommendations have score 0
**Cause:** SVD transform producing zero vector (very rare query)
**Fix:** Add a fallback that returns products sorted by cluster diversity when all scores are 0.

### Wrong seasonal recommendations
**Cause:** `isColdFabric()` list doesn't include the fabric
**Fix:** Add the fabric to the `COLD_FABRICS` array in `mlRecommend.ts`.

## OpenAI Errors

### "This model's maximum context length is exceeded"
**Cause:** Chat history is too long
**Fix:** Truncate conversation history to last N messages. Keep system prompt + last 10 messages.

### "Rate limit exceeded" (429)
**Cause:** Too many API calls per minute
**Fix:** Implement exponential backoff retry. Switch to HuggingFace fallback temporarily.

### "Invalid API key" (401)
**Cause:** Wrong or expired API key
**Fix:** Check `OPENAI_API_KEY` in `.env.local`. Visit platform.openai.com to verify key.

### JSON parse error from GPT response
**Cause:** GPT returned non-JSON despite JSON mode
**Fix:** Add try/catch around `JSON.parse()`. Fall back to regex extraction. Ensure prompt says "return JSON."

## Modal/Try-On Errors

### Modal cold start timeout
**Cause:** First request after Modal container recycled. Model loading takes 3-5 min.
**Symptom:** Frontend shows error after 11-minute timeout
**Fix:** The Modal service shows "container starting" in Modal dashboard. Users need to wait or retry. Pre-warming (calling `/health` periodically) is implemented in the Express backend (pings every 4 minutes).

### "CUDA out of memory"
**Cause:** A10G GPU memory (24GB) exhausted (rare at default settings)
**Fix:** Reduce `num_inference_steps` to 10. Reduce input image resolution to 512×768.

### "Model not found" in Modal volume
**Cause:** Modal volume was reset or model files corrupted
**Fix:** Run `modal volume rm stylesense-ootd-cache` and redeploy. Models will re-download (~4GB, ~5 min).

### OOTDiffusion garment bleeding
**Cause:** Garment cleaning (ONNX step) didn't cleanly remove model's body from garment photo
**Fix:** Adjust `GARMENT_LABEL` threshold in `clean_garment_with_onnx()`. Try with different garment image (plain white background works best).

## HuggingFace Errors

### "Model is currently loading"
**Cause:** HuggingFace Inference API loads model on first request (cold start ~1-2 min)
**Fix:** Retry with exponential backoff. Show "AI is warming up..." message to user.

### Response is empty or truncated
**Cause:** `max_new_tokens` too low
**Fix:** Increase `max_new_tokens` to 500. Check HuggingFace model card for recommended settings.

## Weather Errors

### Weather shows wrong city
**Cause:** IP geolocation is approximate
**Fix:** This is expected behavior. Geolocation will update when user grants browser permission.

### Weather API "key invalid" error
**Cause:** WeatherAPI.com key expired or hit limits
**Fix:** Generate new key at weatherapi.com. Update `config.ts`.

**Q1: What is machine learning and how does StyleSense.AI use it?**

**Answer:** Machine learning (ML) is a type of artificial intelligence where a computer learns patterns from data without being explicitly programmed with rules.

StyleSense.AI uses ML in three ways:
1. **TF-IDF + SVD** — Understands text queries like "casual blue winter shirt" and finds matching shirts in the catalog
2. **KMeans Clustering** — Groups the 30 shirts into style clusters so similar items appear together
3. **OOTDiffusion** — A deep learning model that generates realistic "you wearing the garment" images

**Viva Answer:** "StyleSense.AI uses ML for both recommendation (TF-IDF with semantic analysis to match user queries to products) and visual generation (the OOTDiffusion diffusion model for virtual try-on). We also use pre-trained deep learning for garment segmentation via an ONNX human parser."

---

**Q2: What is a diffusion model? How does OOTDiffusion work?**

**Answer:** A diffusion model is a type of generative AI that learns to create images by:
1. **Forward process:** Starting with a real image and gradually adding random noise until it becomes pure noise
2. **Reverse process (generation):** Learning to reverse this — starting from pure noise and gradually removing noise to create a new image

**OOTDiffusion specifically:**
- Takes a person photo and a garment photo as inputs
- Uses special "conditioning" to guide the diffusion process so the output shows the person wearing that specific garment
- Runs for 20 "denoising steps" where each step brings the image closer to the final result

**Viva Answer:** "OOTDiffusion is a latent diffusion model that extends Stable Diffusion with outfitting cross-attention — it conditions image generation on both the person's pose and body shape AND the garment's appearance. Starting from random noise, 20 denoising steps guided by these two conditions produce a photorealistic try-on result."

---

**Q3: What is TF-IDF?**

**Answer:** TF-IDF stands for Term Frequency-Inverse Document Frequency. It's a technique to measure how important a word is to a specific document in a collection.

- **TF (Term Frequency):** How often the word appears in the query (more = more important)
- **IDF (Inverse Document Frequency):** How rare the word is across all shirts (rarer = more important)

**Example:** In our 30-shirt catalog:
- "shirt" appears in all 30 shirts → IDF ≈ 0 (very common, not informative)
- "flannel" appears in 3 shirts → IDF ≈ 2.3 (rare, very informative)

So "flannel" in a query is much more valuable for finding the right shirt.

---

**Q4: What is GPT-4o-mini and why did you use it?**

**Answer:** GPT-4o-mini is OpenAI's efficient language model — a smaller, faster, and cheaper version of GPT-4. It can understand text and images (multimodal).

We use it for:
1. **Chatbot** — Answering styling questions
2. **Image validation** — Checking if a person photo is suitable for try-on
3. **Caption generation** — Creating social media captions from try-on result images
4. **Outfit formatting** — Turning ML recommendation scores into natural language

**Why GPT-4o-mini instead of GPT-4?** GPT-4o-mini is 80% cheaper and 2x faster, with sufficient quality for fashion advice. We only upgrade to full GPT-4 Vision capabilities when analyzing images.

---

**Q5: What is ONNX and why is it used?**

**Answer:** ONNX (Open Neural Network Exchange) is an open format for AI models. It allows training a model in one framework (like PyTorch) and running it efficiently in another (ONNX Runtime).

**Why We Use ONNX for Garment Parsing:**
- The human parsing model was trained in PyTorch
- ONNX Runtime can run this model much faster (2-5x) and with lower memory usage than full PyTorch
- ONNX is hardware-agnostic — runs well on both CPUs and GPUs
- Smaller file size — ONNX models are more compact than PyTorch checkpoints

**Q7: What is LSA (Latent Semantic Analysis) and why is it better than simple keyword search?**

**Answer:** LSA (Latent Semantic Analysis) uses SVD (Singular Value Decomposition) to reduce text to lower-dimensional "latent topic" space.

**Simple Keyword Search Problem:**
```
Query: "relaxed fit top"
Product: "Casual Loose Shirt"
→ No word overlap → similarity = 0 → Not recommended
```
This product is clearly relevant but keyword search misses it.

**LSA Solution:**
Both "relaxed" and "casual" appear in similar contexts across all shirt descriptions (both with "cotton", "everyday", "jeans"). SVD discovers this pattern and maps them to similar latent directions. Now:
```
Query LSA vector: [0.3, -0.1, 0.4, ...]
Product LSA vector: [0.28, -0.09, 0.38, ...]
→ High cosine similarity → Recommended!
```

LSA understands semantic relationships, not just exact word matches.

**Q8: How does ControlNet work in the refinement step?**

**Answer:** ControlNet is a neural network that adds spatial conditioning to Stable Diffusion. It allows guiding image generation with structural information (edges, depth maps, poses).

**In StyleSense.AI:**
1. Apply Canny edge detection to the garment image → produces edge map (lines showing garment shape)
2. ControlNet conditions SD generation on these edges
3. Result: garment texture is sharpened while respecting the exact garment shape

**Why Needed:** OOTDiffusion can sometimes produce slightly soft garment edges or lose fine fabric texture. The ControlNet pass sharpens these while keeping the person's face and body unchanged (low `strength=0.3` means the SD pass mostly refines, not regenerates).

**Q10: Why does the try-on endpoint have an 11-minute timeout? Isn't that too long?**

**Answer:** OOTDiffusion on an A10G GPU takes 30-60 seconds for one try-on with 20 inference steps. However, there are two potential delays:

1. **Cold Start:** If the Modal container is idle and gets recycled, the first request triggers model loading (~3-5 minutes — downloading 8GB+ of weights from HuggingFace, loading them into VRAM)
2. **Generation:** The actual inference takes 30-60 seconds

11 minutes = maximum cold start (5 min) + generation (1 min) + network overhead (1 min) + buffer (4 min)

**Mitigation:** The Express backend pings the Modal health endpoint every 4 minutes, keeping the container warm so users rarely experience the 3-5 minute cold start. With a warm container, response time is typically 60-90 seconds.

**Q12: What are the limitations of the current TF-IDF approach and how would you address them?**

**Answer:**

**Current Limitations:**
1. **Vocabulary Mismatch:** If user asks for "chic" but catalog uses "stylish," TF-IDF misses it (LSA helps partially but not fully)
2. **No Context Understanding:** "I don't want blue" is treated same as "I want blue" (negation is ignored)

4. **No Learning:** The model doesn't improve from user interactions

**Solutions:**
1. Replace TF-IDF with sentence embeddings (BERT, Sentence-Transformers) for better semantic understanding
2. Add negation detection: parse "not", "don't want" → exclude matching items
3. Create an API endpoint that accepts new catalog items, computes embeddings, and updates the vector index dynamically
4. Implement implicit feedback learning: items that users click "Try On" get higher weight in future queries

**Q13: Explain the business cost of a wrong garment category detection and how to prevent it.**

**Answer:**

**Business Cost of Wrong Category Detection:**
- If "upper_body" garment is classified as "lower_body"
- OOTDiffusion tries to fit the shirt onto the person's legs
- Result is visually nonsensical
- User experience damaged, GPU time wasted ($0.02-0.05 per failure)
- At scale (1000 users/day): 5% error rate = 50 failed try-ons/day = $1-2.50/day wasted + user churn

**Prevention Measures:**
1. **Confidence threshold:** The ONNX parser returns pixel counts per category. If the difference between top-2 categories is < 20%, reject with "Please upload a clearer garment image."
2. **User override:** Show a "Detected: Upper Body" banner with an option to change. Users know what they uploaded.
3. **Pre-processing standards:** Instruct users to upload garment images with white/plain backgrounds — reduces parser errors.
4. **Evaluation metrics:** Measure category detection accuracy on a held-out garment test set. Set production threshold at 95% accuracy.

**Q14: How does the DWpose model work in the context of try-on?**

**Answer:** DWpose (Dual Whole-body Pose estimation) is a pose estimation model that detects 133 body keypoints including face, body, and hands.

**In Try-On Context:**
1. DWpose analyzes the person photo → 133 keypoints (shoulders at (x1,y1), elbows at (x2,y2), etc.)
2. These keypoints define the person's pose — arm angles, body tilt, position
3. OOTDiffusion uses the pose to understand WHERE to place the garment
4. The garment is warped to fit the detected pose (shoulders width determines shirt shoulder width, etc.)

**Why Pose Matters:** Without pose, the diffusion model doesn't know if arms are raised or hanging — the garment would look unnaturally rigid. Pose conditioning makes try-on results realistic even for unusual poses (arms raised, walking stance, etc.).

**Q15: What is the role of `guidance_scale=2.0` in OOTDiffusion?**

**Answer:** `guidance_scale` controls how closely the output follows the conditioning signal (the garment appearance) vs. the model's own creative interpretation.

- `guidance_scale = 1.0` → Output ignores garment conditioning (random generation)
- `guidance_scale = 2.0` → Balanced: follows garment closely but allows natural draping/wrinkles
- `guidance_scale = 5.0+` → Very strict garment adherence, but may produce artifacts

**Default 2.0 Rationale:** Fashion try-on requires the garment to look like the original product (2.0 is high enough) but also need natural physical behavior — fabric draping, light reflection, fit on the body (lower values allow this). Values > 3 tend to produce "pasted on" looking results rather than naturally worn clothing.

**Viva Answer:** "The guidance scale is the classifier-free guidance weight. At 2.0, it balances faithfulness to the input garment's appearance against physically plausible garment behavior. Higher values produce more faithful but less natural results; lower values produce more natural but less faithful garment reproduction."

**Q17: What does L2 normalization do and why is it applied to the LSA matrix?**

**Answer:** L2 normalization scales a vector so its length (L2 norm / Euclidean length) equals 1.

**Formula:** `v_normalized = v / ||v||₂`

**Why Applied in LSA Context:**

Without normalization, cosine similarity requires dividing by both vectors' norms:
```
cosine(A, B) = (A · B) / (||A|| × ||B||)
```

With normalization (both A and B have ||v|| = 1):
```
cosine(A_norm, B_norm) = A_norm · B_norm  (just dot product!)
```

**Practical Benefits:**
1. Faster computation (dot product only, no division at query time)
2. Scale-invariant (longer descriptions don't dominate just because they have more words)
3. Pre-computing normalized LSA vectors for all 30 shirts stores them in `lsaMatrixNorm` — query-time similarity reduces to a single matrix multiplication

**Q18: How do you keep the Modal GPU service warm to avoid cold starts?**

**Answer:** The Express backend (`server.js`) pings the Modal health endpoint every 4 minutes:

```javascript
// server.js
const PING_INTERVAL = 4 * 60 * 1000; // 4 minutes

setInterval(async () => {
  if (TRYON_MODAL_URL) {
    try {
      await fetch(`${TRYON_MODAL_URL}/health`);
      console.log('Modal ping: warm');
    } catch (err) {
      console.warn('Modal ping failed:', err.message);
    }
  }
}, PING_INTERVAL);
```

Modal recycles idle containers after ~5 minutes. By pinging every 4 minutes, we keep the container alive and avoid the 3-5 minute cold start for most users.

**Trade-off:** This costs ~$0.003/hour (A10G is billed when warm but idle) to save 3-5 minutes of user wait time. For a production app with active users, this is worth it.

**Q19: How would you scale the try-on service to handle 100 concurrent users?**

**Answer:** 

**Current State:** Modal's default concurrency allows multiple containers. Each try-on takes 60 seconds on one A10G. 100 concurrent users = need 100 parallel containers.

**Scaling Strategy:**
1. **Modal Concurrency:** Set `allow_concurrent_inputs=True` in `@app.function()`. Modal auto-scales containers based on queue length.

2. **Batch Processing:** Accumulate 4 requests → run in one batch (OOTDiffusion supports batch inference) → 4× throughput on same GPU

3. **Queue System:** Add Redis/BullMQ job queue in Express backend. Users receive a job ID immediately, poll for completion. No HTTP timeout issues.

4. **Cost at Scale:** 100 concurrent × $1.10/hr × 60 sec ≈ $3.06/hour for GPU. At 100 users: ~$0.02-0.05/user for a complete try-on.

5. **Cheaper GPU Option:** A10G is premium. For cost reduction, T4 (cheaper, slower) can handle try-on in ~2-3 minutes instead of 60 seconds — acceptable for non-premium tiers.
